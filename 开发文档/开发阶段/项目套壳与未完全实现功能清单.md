## 详细说明

### 1. `mem clear` 只打印成功

当前代码：

```python
@app.command()
def clear(force: bool = False):
    """清空所有记忆"""
    if not force:
        confirm = typer.confirm("确定要清空所有记忆吗？此操作不可恢复！")
        if not confirm:
            return
    typer.echo("✅ 记忆已清空")
```

问题：

- 没有调用后端接口。
- 没有删除 `memories` 表。
- 没有删除 `decision_memories` 表。
- 没有删除 ChromaDB 向量库记录。

影响：

- 用户以为数据已清空，但数据库中仍然存在。
- 这是当前最典型的“有入口但没实现”的功能。

建议：

1. 后端新增 `DELETE /api/v1/memory/clear`。
2. 删除 `DecisionMemory`、`Memory` 关系库数据。
3. 清理 ChromaDB collection，或逐条删除向量记录。
4. `mem clear` 调用该接口，并展示实际删除数量。

### 2. 飞书决策抽取不是 LLM

当前代码通过规则实现：

- `DECISION_MARKERS`
- `_extract_project()`
- `_extract_reason()`
- `_extract_preferred_terms()`
- `_extract_rejected_terms()`

问题：

- 文档中多处写到“通过 LLM API 解析结构化决策”，但代码没有调用 LLM。
- 只能处理较明确的句式，例如“以后统一用 prod”“不再使用 staging”。
- 对多人讨论、隐式结论、反对意见、备选方案的理解不足。

影响：

- 方向 B 的“从对话/文档中自动提取决策、理由、反对意见、结论”还没有完整实现。

建议：

1. 新增 `core/decision_extractor.py`。
2. 使用 LLM 输出固定 JSON schema。
3. 字段包含 `decision`、`topic`、`reason`、`opposition`、`accepted_option`、`rejected_options`、`project`、`confidence`。
4. 规则抽取保留为 LLM 失败时的 fallback。

### 3. 飞书交互卡片尚未实现

当前实现：

- `_memory_to_card()` 返回内部 JSON 卡片结构。
- `_cards_to_text()` 把卡片转换成纯文本。
- SDK 当前发送的是 `msg_type=text`。

问题：

- 不是飞书官方交互卡片。
- 没有按钮、复制命令、展开步骤、风险提示等交互能力。

影响：

- 演示观感弱于文档中“历史决策卡片”“CLI 命令卡片”的描述。

建议：

1. 新增 `feishu_bot/card_templates.py`。
2. 生成飞书 interactive card JSON。
3. 支持三类卡片：
   - 决策卡片
   - CLI 命令卡片
   - 工作流步骤卡片
4. 发送层支持 `msg_type=interactive`。

### 4. 飞书 SDK 长连接未在真实企业应用中验证

当前代码：

- `feishu_bot/sdk_events.py`
- `scripts/run_feishu_sdk_events.py`

已做的事情：

- 懒加载 `lark_oapi`。
- 构建 `EventDispatcherHandler`。
- 注册 `P2ImMessageReceiveV1`。
- 把 SDK 事件转发到 `/api/v1/feishu/message/analyze`。

问题：

- 当前单测只验证了事件对象转换和后端转发。
- 没有真实连接飞书企业自建应用的集成测试记录。
- 当前运行环境曾出现 `ModuleNotFoundError: No module named 'lark_oapi'`，说明依赖未必安装到实际环境。

影响：

- 代码链路看起来完整，但真实飞书群消息能否稳定进入后端还需要实际联调证明。

建议：

1. 补充真实飞书联调记录。
2. 在启动脚本中打印 App ID、后端 URL、订阅状态。
3. 增加 `python scripts/check_feishu_env.py` 环境检查脚本。

### 5. SDK 自动回复依赖真实飞书应用权限

当前代码：

- `feishu_bot/sdk_messages.py`
- 调用 `client.im.v1.message.create()`

问题：

- 需要安装 `lark-oapi`。
- 需要 `FEISHU_APP_ID` / `FEISHU_APP_SECRET`。
- 飞书应用需要具备发送消息权限。
- 当前测试只 mock 了 SDK 请求构造，没有真实发消息测试。

影响：

- SDK 发送配置不正确时，数据库仍可更新，但群里不会收到回复。

建议：

1. 增加启动前检查。
2. 支持自定义机器人 webhook 作为轻量发送通道。
3. 增加真实飞书发送联调记录。

### 6. 自定义机器人尚未支持

当前状态：

- 用户问过“能不能用自定义机器人”，目前代码没有实现。
- 只有企业自建应用 SDK 接收事件和 SDK 发送消息。

问题：

- 自定义机器人不能接收群消息，只适合作为发送通道。
- 代码中尚未封装自定义机器人 webhook。

建议：

1. 新增 `FEISHU_SEND_PROVIDER=sdk/custom_webhook`。
2. 新增 `FEISHU_CUSTOM_BOT_WEBHOOK`。
3. 实现 `feishu_bot/custom_webhook.py`。

### 7. Shell completion 还没有真实接入

当前状态：

- `mem suggest` 已实现。
- 文档中多处提到“后续接入 PowerShell/Bash/Zsh completion”。

问题：

- 没有生成 completion 脚本。
- 用户输入命令前不会自动弹出建议。
- 当前只能手动执行 `mem suggest docker`。

建议：

1. 新增 `mem completion install --shell powershell/bash/zsh`。
2. PowerShell 通过 `Register-ArgumentCompleter` 接 `mem suggest`。
3. Bash/Zsh 生成对应 completion 文件。

### 8. `mem watch` 不是实时监听

当前实现：

- 读取历史文件。
- 统计命令出现次数。
- 超过阈值后调用 `/cli/command/record`。

问题：

- 命令名叫 `watch`，但不是实时监听。
- 不会在用户每次执行命令后立刻记录。
- 执行成功率只有 `mem search --execute` 或工作流执行时能记录，普通终端命令不会记录 exit code。

建议：

1. 改名为 `scan-history`，或实现真正后台 watch。
2. 提供 shell hook，把每次命令和 exit code 发给后端。
3. 与 completion 一起做成 shell 集成安装流程。

### 9. 多轮讨论聚合未实现

当前状态：

- `handle_feishu_message()` 逐条处理消息。
- 一条消息里如果没有明显决策关键词，就不会入库。

问题：

- 真实飞书决策通常分散在多条消息中。
- 当前无法理解：

```text
A：staging 最近老出问题
B：那 project-a 后面切 prod？
C：确认，就这么定
```

建议：

1. 引入 `conversation_buffer`。
2. 按 `chat_id + topic + 10分钟窗口` 聚合。
3. 由 LLM 对窗口内容进行决策抽取。

### 10. 决策权限与可信度未实现

当前状态：

- 任何包含决策关键词的消息都可能入库。

问题：

- 普通成员一句“以后用 X”也会覆盖旧决策。
- 没有负责人、管理员、确认词、置信度判断。

建议：

1. 配置 `FEISHU_TRUSTED_USER_IDS`。
2. 只有可信用户或出现“确认/拍板/最终决定”等词时正式入库。
3. 低置信度决策存为 `pending`，需要人工确认。

- 群内查询提效指标。

建议：

新增：

```text
test/data/feishu_decision_effectiveness_dataset.json
tests/evaluation/test_feishu_decision_effectiveness_dataset.py
```

### 12. README 中飞书端描述偏演示化

README 写到：

```text
机器人自动回复：好的，我记住了...
主动推送卡片：历史决策提醒
```

当前代码：

- 可以自动回复文本，但依赖 `FEISHU_AUTO_REPLY=true` 和飞书应用发送权限。
- 尚未实现真实飞书交互卡片。

建议：

1. README 标注飞书端需要企业自建应用、SDK 事件订阅和发送消息权限。
2. 将“卡片”改为“文本回复 / 内部卡片 JSON，交互卡片待接入”。

### 13. 向量库异常静默降级

当前代码：

```python
try:
    embedding = get_embedding(memory_data.content)
    vector_client.add_memory(...)
except Exception:
    pass
```

优点：

- 关系库保存不会因为 OpenAI 或 ChromaDB 异常失败。

问题：

- 用户不知道向量库是否真的写入成功。
- 语义检索可能悄悄退化成关键词搜索。

建议：

1. 打日志。
2. 增加 `/health/vector`。
3. 在保存返回值中增加 `vector_status`。

### 14. `DecisionMemory.deadline` 未填充

模型中有：

```python
deadline = Column(DateTime, index=True)
```

当前抽取逻辑没有识别截止日期。

影响：

- 赛题提到“上周五确认截止日期是 5 号”这类时间关联，目前没有结构化支持。

建议：

1. 增加日期解析。
2. LLM 抽取时输出 `deadline`。
3. 检索时支持按时间排序和提醒。

### 15. 飞书文档记忆未实现

数据模型和文档中提到：

```text
source = feishu_doc
```

当前代码主要支持：

- `cli`
- `feishu_group`

问题：

- 没有飞书文档读取、解析、决策抽取入口。

建议：

1. 新增飞书文档 webhook 或定时同步。
2. 解析文档评论/正文。
3. 存入 `source=feishu_doc`。

## 优先修复建议

建议按优先级处理：

1. **P0：实现 `mem clear` 真删除**  
   这是最明显的“按钮有了但功能没做”，用户最容易踩坑。

2. **P0：修正 README 和技术文档中超前描述**  
   避免答辩或演示时被问到“卡片在哪里”“LLM 在哪里”。

3. **P1：飞书决策 LLM 抽取**  
   这是方向 B 从规则 demo 升级为赛题完整能力的关键。

4. **P1：飞书交互卡片或自定义机器人发送通道**  
   提升真实群内演示效果。

5. **P1：方向 B evaluation 测试集**  
   用数据证明系统有效性，补齐比赛要求中的说服力。

6. **P2：Shell completion 和真实 watch**  
   提升方向 A 的真实终端体验。

## 当前已经比较扎实的部分

为避免误判，下面这些不是套壳，已经有实际代码和测试支撑：

1. CLI 命令记录与推荐：`/cli/command/record`、`/cli/command/suggest`。
2. 真实 SQLite 记忆存储：`memories` 表和 `decision_memories` 表。
3. CLI 工作流保存与执行：`mem workflow save/run`。
4. 中文意图和关键词搜索兜底：`backend/routers/memory.py`。
5. 矛盾更新基础机制：`inactive`、`supersedes`、`superseded_by`。
6. CLI evaluation 测试：抗干扰、矛盾更新、效率指标。
7. 飞书消息进入后端后的方向 B 核心链路：`/api/v1/feishu/message/analyze`。
8. 飞书决策干预 CLI 推荐排序：`backend/routers/cli.py` 中的 `_decision_policy_score()`。
