# CLI vs. 飞书群聊：技术路线对比详解

## 一、 核心差异概览

| 对比维度 | CLI 命令行 | 飞书群聊 |
| :--- | :--- | :--- |
| **交互模式** | **同步请求-响应** (Synchronous Request-Response) | **异步事件驱动** (Asynchronous Event-Driven) |
| **用户意图** | **明确、结构化** (如 `mem memorize ...`) | **模糊、非结构化** (自然语言对话) |
| **触发方式** | 用户主动执行特定命令 | 用户在群聊中 `@机器人` 或触发关键词 |
| **数据来源** | 标准化的命令参数 | 加密的JSON事件包 |
| **反馈形式** | 终端标准输出 (stdout/stderr) | 飞书卡片消息或文本消息 |
| **核心挑战** | 命令补全、上下文感知、无缝集成Shell | 意图识别、自然语言理解、事件安全校验 |

## 二、 CLI 技术路线详解

CLI路线的核心是为开发者提供一个“第二大脑”，能记住并推荐常用的、复杂的命令。

### 2.1. 端到端流程

```mermaid
graph TD
    subgraph 开发者终端 (Developer's Terminal)
        A[用户输入: mem search "部署"] --> B[Typer CLI 应用];
    end

    subgraph 本地客户端 (Local Client)
        B -- HTTP POST --> C[后端API: /api/v1/memory/retrieve];
    end

    subgraph 后端服务 (Backend Service)
        C -- 调用 --> D[核心检索模块 Retriever];
        D -- 返回结果 --> C;
    end

    subgraph 本地客户端
        C -- HTTP 200 OK --> B;
        B -- 格式化输出 --> E[终端显示结果];
    end
```

### 2.2. 详细步骤拆解

1.  **用户执行命令** (`cli/main.py`)
    用户在终端中输入 `python -m cli.main search "部署命令"`。
    *   `Typer` 库解析这个命令，识别出主命令是 `search`，参数是 `"部署命令"`。

2.  **客户端发起API请求** (`cli/main.py`)
    *   CLI应用作为一个标准的HTTP客户端，使用 `requests` 库向后端API网关 `http://localhost:8000/api/v1/memory/retrieve` 发起一个 `POST` 请求。
    *   请求体 (Body) 是一个JSON对象：`{"query": "部署命令", "top_k": 5}`。
    *   **关键点**：这是一个**同步阻塞**的过程。CLI应用会一直等待，直到收到后端的HTTP响应。

3.  **后端处理请求** (`backend/routers/memory.py` -> `core/retriever.py`)
    *   FastAPI接收到请求，并将其路由到 `retrieve_memories` 函数。
    *   函数调用核心检索模块 `core.retriever.search_memories`。
    *   检索模块执行**混合检索**（语义向量+关键字），从数据库中找出最相关的记忆。
    *   将检索到的记忆列表作为JSON数据，通过HTTP响应返回给CLI客户端。

4.  **客户端渲染结果** (`cli/main.py`)
    *   CLI应用收到HTTP响应，检查状态码是否为200。
    *   如果成功，解析响应中的JSON数据。
    *   使用 `typer.echo()` 或 `print()` 将结果格式化后输出到终端的标准输出（stdout），用户就能在屏幕上看到检索到的命令列表。
    *   如果API请求失败，则将错误信息输出到标准错误（stderr）。

### 2.3. 上下文感知与命令补全（进阶）

*   **上下文感知**：CLI客户端可以做得更智能，比如在发起API请求时，自动附带当前的工作目录路径 (`cwd`)、Git分支等信息。后端可以利用这些上下文来过滤和排序检索结果，实现“在项目A中推荐部署命令X，在项目B中推荐Y”。
*   **命令补全**：通过集成 `shell` 的 `completion` 机制（如 `bash`, `zsh`），当用户输入 `mem search` 并按下 `Tab` 键时，CLI可以实时调用后端的 `/api/v1/cli/command/suggest` 接口，获取推荐的查询关键词，实现动态补全。

## 三、 飞书群聊技术路线详解

飞书路线的核心是将一个无状态的聊天机器人，转变为一个有记忆、能理解上下文的智能助理。

### 3.1. 端到端流程

```mermaid
graph TD
    subgraph 飞书客户端 (Feishu Client)
        A[用户发送: @机器人 记住...] --> B[飞书开放平台];
    end

    subgraph 后端服务 (Backend Service)
        B -- Webhook POST --> C[事件回调接口 /api/v1/feishu/event/callback];
        C -- 安全校验 --> D[事件处理器 EventHandler];
        D -- 意图识别 --> E{判断是'记忆'还是'查询'};
        E -- '记忆' --> F[记忆提取模块 Extractor];
        F -- 调用LLM --> G[记忆存储模块 Storage];
        G -- 双写 --> H[数据库(PG+Chroma)];
        G -- 确认消息 --> I[消息推送模块 Pusher];
    end

    subgraph 飞书开放平台
        I -- 调用API --> B;
    end

    subgraph 飞书客户端
        B -- 推送消息 --> J[群聊中显示确认卡片];
    end
```

### 3.2. 详细步骤拆解

1.  **用户发送消息**
    用户在飞书群聊中 `@机器人` 并发送消息。

2.  **飞书平台推送事件**
    *   飞书服务器捕获这个 `@` 事件，并将其打包成一个**加密的JSON数据包**。
    *   飞书向我们在其开发者后台配置的**Webhook URL** (`https://<your-domain>/api/v1/feishu/event/callback`) 发起一个 `POST` 请求。
    *   **关键点**：这是一个**异步**过程。飞书平台只负责“通知”我们的后端，它不会等待我们的处理结果，只要收到一个HTTP 200的响应就认为通知成功。

3.  **后端接收与安全校验** (`backend/routers/feishu.py`)
    *   后端接口收到请求。
    *   **第一重安全**：验证请求头中的 `X-Lark-Signature` 签名，确保请求确实来自飞书，而不是恶意攻击。这是通过 `Verification Token` 实现的。
    *   **第二重安全**：使用 `Encrypt Key` 解密请求体，获取原始的、明文的事件JSON。
    *   **立即响应**：为了防止飞书平台因超时而重试，后端在完成安全校验后，应尽快返回一个 `HTTP 200 OK` 响应给飞书。真正的业务处理在后台异步进行。

4.  **后台任务：意图识别与处理** (`feishu_bot/event_handler.py`)
    *   事件处理器分析明文JSON，提取出消息内容、发送者、群ID等信息。
    *   **调用LLM进行意图识别**：将消息文本（如 `“记住，项目alpha版的最终上线日期定在5月10日。”`）发送给大模型，让其判断用户的意图是“储存记忆”、“查询记忆”还是“闲聊”。
    *   根据LLM返回的意图，进入不同的处理分支。

5.  **“储存记忆”分支** (`core/extractor.py` -> `core/storage.py`)
    *   如“内部技术文档”中所述，调用LLM从文本中提取结构化信息。
    *   调用存储模块，将结构化数据和向量数据**双写**到关系型数据库和向量数据库。

6.  **异步反馈：调用飞书API推送消息** (`feishu_bot/message_push.py`)
    *   记忆成功存储后，为了给用户一个交代，后端服务需要**主动**调用飞书开放平台的 `im/v1/messages` API。
    *   在调用此API时，需要提供 `App ID` 和 `App Secret` 来获取 `tenant_access_token`，作为API调用的凭证。
    *   构造一个精美的卡片消息JSON，通过API发送回原来的群聊。用户就会看到机器人发出的“我记住了”的确认卡片。

## 四、 总结

| 对比项 | CLI | 飞书群聊 |
| :--- | :--- | :--- |
| **通信模型** | 客户端-服务器 (Client-Server) | 发布-订阅 (Publish-Subscribe) + 回调 |
| **数据流** | 单向同步：`请求 -> 处理 -> 响应` | 双向异步：`事件推送 -> 处理 -> API调用` |
| **安全机制** | 标准API认证 (如JWT, API Key) | **签名校验 + 加解密** (飞书特定机制) |
| **状态管理** | 无状态（每次请求独立） | 需要管理会话状态和上下文（哪个群、哪个用户） |
| **实现复杂度** | 相对较低，是标准的Web服务消费模式 | 相对较高，涉及异步任务、安全校验、API回调等复杂流程 |

总而言之，CLI路线是一个直接、高效的工具化集成，而飞书群聊路线则是一个更智能、更复杂的生态化集成，它要求系统不仅能“听懂”，还要能“回应”，并且整个过程必须安全、可靠、异步。
