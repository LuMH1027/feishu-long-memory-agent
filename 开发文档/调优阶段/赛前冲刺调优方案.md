| 维度 | 权重 | 评委在看什么 | 我们的发力点 |

## 二、P0 调优项（必须完成，直接影响评分）

### 1. Demo 脚本零失误保障

**现状**：`demo/auto_log.py` 和 `demo/demo_record.py` 已开发完成，但存在因环境差异导致失败的隐患。

**调优动作**：

- [ ] **环境自检脚本**：开发 `scripts/preflight_check.py`，运行 Demo 前一键检查所有依赖
  ```
  检查项：Python 版本、依赖包完整性、.env 配置、数据库状态、Embedding 服务可达性
  ```
- [ ] **数据库重置改为独立脚本**：当前 `--reset-db` 必须在后端启动前执行，容易出现时序错误。抽离为独立操作，避免失误
- [ ] **飞书 SDK 环境 Mock 模式**：当 `lark-oapi` 未安装或飞书凭证未配置时，自动切换到 API 模拟模式，确保后端+CLI 部分能完整演示
- [ ] **录屏脚本添加断点续跑**：如果在步骤 N 出错，可以从步骤 N 重新开始，不用从头跑

**对应评分维度**：完整性&价值（Demo 稳定可演示）

**预计耗时**：4 小时

---

### 2. 双向联动闭环可视化强化

**现状**：飞书决策 → CLI 排序已有 `_decision_policy_score()` 实现，但 Demo 中展示不够直观。

**这也是我们与 Wiki Bot / AI Notetaker 最大的区分点，必须让评委一眼看懂。**

**调优动作**：

- [ ] **CLI suggest 输出增加"决策影响"标签**：当某条命令的排序被飞书决策影响时，在输出中加 `[决策优先]` 标签
  ```
  $ mem suggest docker
  1. docker-compose -f prod.yml up -d     [决策优先] 飞书群决议: 统一用 prod 环境
  2. docker-compose -f staging.yml up -d  [已废弃]   飞书群决议: 不再使用 staging
  ```
- [ ] **search 结果展示决策来源**：搜索结果中飞书决策类型的记忆，标注来源群聊和时间
- [ ] **Demo 中增加"反向验证"环节**：先展示 CLI 中某命令的使用频率（无决策影响时排在第二位），再演示飞书决策发送后该命令升至第一

**对应评分维度**：完整性&价值（闭环完整）+ 创新性（差异化亮点）

**预计耗时**：3 小时

### 3. Demo 录屏脚本节奏优化

**现状**：当前脚本 ~12 分钟，覆盖面广但节奏偏平。评委注意力在前 3 分钟定生死。

**调优动作**：

- [ ] **前 3 分钟高密度爆点**：
  - 第 1 分钟：语义搜索（"启动webapp容器" → 找到 docker 命令）— 最直观的 AI 能力
  - 第 2 分钟：矛盾更新（"不对，改成 B"→ 旧记忆自动作废）— 最亮的架构设计
  - 第 3 分钟：跨域联动（飞书发决策 → CLI 搜索出现飞书结果）— 最大差异化
- [ ] **缩短自动脚本演示**：自动部分加速到 1.5x，留更多时间给手动交互环节
- [ ] **每个手动环节加一句话总结**：操作完成后口述一句话点题，帮助评委理解

**对应评分维度**：路演表现

**预计耗时**：2 小时（调整脚本 + 练习）

### 4. 评委 Q&A 预案库

**现状**：缺少针对评委可能提问的准备。

**调优动作**：

- [ ] **准备 10 个高频问题的回答**：

| 预期问题 | 回答要点 |
|---------|---------|
| "和 AI 记事本有什么区别？" | 自动抽取 vs 手动录入；跨渠道矛盾检测；CLI 工具链联动 |
| "为什么不用 RAG 直接用？" | 我们是 RAG 的逆向应用——不是检索文档回答问题，而是从对话中提取知识并影响行为 |
| "向量库挂了怎么办？" | 渐进式降级——关系库始终可用，向量库恢复后自动补齐 |
| "准确率多少？" | 自证评测：抗干扰 Hit@1 100%，矛盾更新 100%，效率提升 78% |
| "飞书真的能自动识别决策？" | LLM + 规则双保险——LLM 处理复杂语义，规则保证确定性兜底 |
| "和其他参赛项目比有什么不同？" | 唯一一个桥接开发者 CLI 和团队协作的工具；决策不止存储，反向影响行为 |
| "数据安全怎么保证？" | 当前聚焦核心能力验证，生产部署会接入企业 SSO + 数据加密（诚实回答，展示工程意识） |
| "能扩展到其他平台吗？" | 架构预留了 source 字段，接入钉钉/企微/Slack 只需新增适配层 |
| "怎么处理多轮讨论？" | 当前单轮识别已稳定，多轮聚合窗口在架构中预留了 chat_id + 时间窗口 |
| "技术上最有挑战的是什么？" | 矛盾检测的 topic_key 设计 + ChromaDB 维度自动迁移 + 跨域排序权重平衡 |

- [ ] **准备 1 分钟电梯演讲版本**：如果评委说"给你 1 分钟介绍项目"

**对应评分维度**：路演表现（回答专业度与深度）

**预计耗时**：2 小时

## 六、可用 Skill 推荐

当前项目配置了以下 Skill，可以在调优过程中调用以提升效率：

| 调优动作 | 推荐 Skill | 用途 |
|---------|-----------|------|
| 验证 Demo 流程完整性 | `qa` 或 `qa-only` | Headless 浏览器自动化测试，验证 API 端点和 Demo 步骤 |
| 代码质量复查 | `review` | 对修改后的代码做 diff review，确保不引入新问题 |
| 代码冗余优化 | `simplify` | 扫描新增代码，检查可复用性和效率 |
| Demo 脚本调优讨论 | `office-hours` | 作为产品头脑风暴，讨论 Demo 叙事结构 |
| 架构合理性验证 | `plan-eng-review` | 对系统架构做最终审查，确保答辩时经得起技术拷问 |
| 界面/卡片视觉审查 | `design-review` | 检查飞书卡片的颜色、排版、信息密度 |
| 安全基线检查 | `security-review` | 快速扫描代码中的硬编码凭证、注入风险（答辩前过一遍更安心） |

### 推荐执行顺序

```
Day 1 上午: 先跑 qa → 发现 Demo 流程 bug → 修复
Day 1 下午: 调 review → 检查修改的代码质量
Day 2 下午: 跑 simplify → 清理冗余代码
Day 2 晚上: 跑 security-review → 确保代码中无硬编码密钥
Day 3 上午: 跑 plan-eng-review → 验证架构叙述自洽
Day 3 下午: 最终录屏前跑 design-review → 检查卡片视觉效果
```
