## T2-1. 人审机决 —— 决策卡片打回 + Reaction 确认 ⭐

**现状**：机器人抽取决策后直接入库，无人审核。人只能事后发「更正」覆盖。

**目标流程**：

```
群聊消息 → LLM 抽取决策
  → 机器人发「待确认」卡片 [确认采纳] [打回]
    → 人 👍（Reaction）→ 自动确认 → status=active
    → 人 👎（Reaction）→ 自动删除
    → @机器人 打回 → 附带理由删除 + 追问正确内容
```

**两种打回方式**：

| 方式 | 触发 | 场景 |
|------|------|------|
| Reaction 👍👎 | 飞书 Reaction 事件（无需公网） | 快速表态 |
| @机器人文本 | `@机器人 打回` / `@机器人 这个不对` | 附带纠正理由 |

**实现要点**：

- [x] 卡片增加 [确认采纳] [打回] 按钮 (2026-05-11)
- [x] `feishu_bot/sdk_events.py` 新增 `P2ImMessageReactionV1` 事件处理 (2026-05-11)
- [x] 决策入库改为「先发卡片 → 确认后入库」：`status=pending` (2026-05-11)
- [x] 👍 → active / 👎 → 删除 (2026-05-11)
- [x] 多人 Reaction 加权（3 个 👍 = 高置信度确认）(2026-05-11)
- [x] 超时 5 分钟无人操作 → 自动 active (2026-05-11)
- [x] @机器人文本打回 → 匹配最近 pending 卡片 → 删除 (2026-05-11)

**Demo 高光**：评委看到卡片 → 人 👍 → 决策生效 → 人 👎 → 决策消失。Reaction 替代按钮回调的设计 choice 本身就是创新点。

## T2-7. LLM 消息意图分类 —— 替代硬编码关键词 ⭐

**现状**：用 7 个硬编码中文关键词（`CORRECTION_MARKERS`）判断消息是「更正」还是「新决策」。无法识别隐性纠正、确认、讨论中无结论等场景。

**这是 T4-S3 的前置快赢版——只做分类，不做全链路重构。**

**目标**：

```
每条群消息 → 轻量 LLM 调用（复用现有 extract_decision_with_llm 链路）
  ├── decision_new     → 新决策 → 走抽取 + 待确认卡片
  ├── decision_revise  → 调整已有 → 走矛盾更新流程
  ├── decision_confirm → 确认已有 → 加固置信度，不发新卡片
  ├── decision_repeal  → 废除已有 → 走打回逻辑
  ├── unclear          → 指令模糊 → 机器人主动追问澄清
  ├── query            → 查询意图 → 走检索回复
  └── chat             → 闲聊 → 忽略
```

**新增：`unclear` —— 主动追问机制**

当 LLM 检测到消息中有决策意图但关键信息缺失时，机器人不猜测、不乱入库，而是**主动发追问卡片**：

| 场景 | 消息 | 机器人追问 |
|------|------|-----------|
| 方案有歧义 | "以后用那个新的部署方式" | "你说的「新的部署方式」是指 k8s 还是 docker-compose？" |
| 范围不清楚 | "前端统一换框架" | "是所有项目都换，还是只换新项目？目前哪些项目已经在用？" |
| 缺少结论 | "staging 最近老出问题，prod 会不会好一点" | "你是在提议切换到 prod 吗？还是只是想了解一下 prod 的情况？" |
| 多人讨论无共识 | A: "用 React" B: "Vue 更好" C: "Angular 也不错" | "目前有三种方案在讨论中（React/Vue/Angular），有结论了吗？" |

**追问 → 回复 → 入库的完整闭环**：

```
用户发模糊消息
  → LLM 分类为 unclear + 生成追问内容 + 生成追问卡片
  → 机器人发追问卡片（蓝色，含具体问题和选项按钮）
  → 用户回复明确内容
  → LLM 对回复重新分类 + 抽取
  → 发待确认卡片 → 确认后入库
```

**实现要点**：

- [ ] 分类 Prompt 中增加 `unclear` 类型定义：有决策意图但关键信息缺失
- [ ] `unclear` 输出额外携带 `clarification_question`（追问文本）+ `suggested_options`（可选按钮）
- [ ] 追问卡片用蓝色模板，含问题和最多 3 个选项按钮
- [ ] 用户的追问回复自动关联原消息（通过 `in_reply_to_message_id`），形成对话上下文
- [ ] 追问对话超过 3 轮仍未澄清 → 放弃入库，记录日志

**与规则方式的关键差异**：

| 场景 | 规则结果 | LLM 分类结果 |
|------|---------|-------------|
| "其实上次那个方案不太对" | 不匹配关键词 → 漏判 | `decision_revise` |
| "那就按张工说的做吧" | 不匹配关键词 → 漏判 | `decision_confirm` |
| "以后用那个新的部署方式" | 匹配"以后用" → 误入库（方案不明） | `unclear` → 追问 |
| "这个方案好是好，但预算不够" | 匹配"方案" → 误判为决策 | `chat`（无结论） |
| "@机器人 上次部署流程是什么" | 仅匹配查询词 | `query` + 自动关联话题 |

**实现要点**：

- [ ] 新增 `core/message_classifier.py`：轻量 Prompt，8 类输出 + 置信度 + 追问内容
- [ ] 分类 Prompt 与抽取 Prompt 分离（分类只需判断意图，抽取才需要结构化 JSON）
- [ ] 在 `backend/routers/feishu.py` 的 `handle_feishu_message()` 入口处调用分类
- [ ] `decision_revise` 和 `decision_repeal` → 走已有矛盾更新/打回链路
- [ ] `decision_confirm` → 不加新记忆，仅增加已有记忆的置信度字段
- [ ] `chat` → 直接跳过，不触发任何处理
- [ ] 低置信度（<0.7）回退为规则判断，保持确定性兜底

**Demo 高光**：在 Demo 中用一条「其实上次那个方案不太好，我们改成 Vue3 吧」——旧系统（规则）识别不到，新系统（LLM 分类）准确识别为 `decision_revise` 并自动走矛盾更新。这就是 AI 技术深度的最直接证明。

**对应维度**：AI 技术实现（从规则到语义的跃迁）| **耗时**：2.5h

### S2. 群级记忆共享与隐私边界

```
个人记忆永远不可被他人检索
记忆表新增 scope: private | group:{chat_id}
```

### S3. LLM 消息意图分类

> **T2-7 已实现快赢版本**：8 类分类器（含 `unclear` 主动追问）替代硬编码关键词，低置信度规则兜底。S3 在此基础上的增强包括：task_assignment 意图识别、多轮上下文的意图修正。

```
每条群消息 → 轻量 LLM 分类（T2-7 已实现核心 7 类 + unclear）
  ├── decision_new     → 新决策
  ├── decision_revise  → 调整已有决策
  ├── decision_confirm → 确认已有决策
  ├── decision_repeal  → 废除已有决策
  ├── query            → 检索回复
  ├── task_assignment  → 提取负责人+DDL
  └── chat             → 忽略
```

| 场景 | 规则方式 | LLM 分类 |
|------|---------|---------|
| "其实上次那个方案不太对" | 漏判 | `decision_revise` |
| "那就按张工说的做吧" | 漏判 | `decision_confirm` |
| "这个方案好是好，但预算不够" | 误判为决策 | `chat` |
| "@机器人 上次部署流程" | 只匹配查询词 | `query` + 关联话题 |

**当前建议**：S3 是唯一可在 2-3 天内做到可演示级别的 S 级能力。不依赖飞书企业审批。
