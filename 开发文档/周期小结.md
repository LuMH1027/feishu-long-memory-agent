## 第一周期（4.23 - 4.25）

### 一、核心产出

本周期交付的最满意成果：**完成项目从概念到可执行框架的"从0到1"完整构建**。

基于赛题需求，搭建起一个分层解耦、职责清晰的企业级项目框架，覆盖后端 API、核心记忆引擎、数据库模型、CLI 客户端等所有关键模块的代码骨架，使得项目结构完整、接口定义明确。同时撰写了多份核心设计文档（技术路线对比、应用场景分析、功能覆盖蓝图），将项目的技术选型和实现路线固化为知识资产。

### 二、量化指标

| 指标 | 数据 |
|------|------|
| 代码提交 | 3 次 |
| 新建模块 | 5 个（backend/core/db/cli/feishu_bot） |
| 新建文件 | ~20 个（代码骨架 + 配置文件） |
| 文档产出 | 5 篇（开发计划、环境指南、技术路线、场景分析、README） |

### 三、过程复盘与沉淀

**1. 这周主要搞定了哪些具体环节？**

- **需求分析与架构设计**：通过与 AI 多轮对话，完成了赛题解读、痛点分析、技术路线对比（Embedding 方案 vs 纯关键词方案），最终确定"关系库主存储 + 向量库增强"的双库架构。
- **代码骨架搭建**：用 AI 生成了 FastAPI 后端、SQLAlchemy 模型、Typer CLI、ChromaDB 客户端等模块的初始代码框架，自己补充了依赖注入、配置管理和数据库初始化逻辑。
- **文档沉淀**：让 AI 帮忙整理技术路线对比表和应用场景分析，自己审核修改后形成正式文档。

**2. 过程中有没有遇到什么特别不顺、卡住很久的情况？**

- **技术选型纠结**：最初在"用 LangChain 还是自己封装 Embedding"之间犹豫了很久。AI 给了两种方案的对比，但最终决定自己封装——因为项目规模不需要 LangChain 的重量级依赖，自己封装更轻量可控。
- **破局方式**：画了一张架构图，把每个模块的职责和依赖关系理清楚后，技术选型就自然清晰了。

**3. 有没有什么写得特别顺，下次还能复用的东西？**

- **与 AI 协作的架构设计流程**：先让 AI 列出多种方案的优劣对比表，再自己做最终决策。这个流程高效且不容易遗漏关键因素。
- **项目骨架生成 Prompt**：告诉 AI "帮我搭建一个 FastAPI + SQLAlchemy + Typer 的项目骨架，要求分层解耦，包含 xxx 模块"，一次就能生成结构良好的初始代码。

### 四、本周随手记

- 用 AI 做需求分析时，发现给它足够的上下文（赛题原文 + 评分标准）比泛泛地问"帮我分析这个项目"效果好很多。
- 代码骨架不需要写得太细，先把接口定义和模块边界定好，具体实现留到下个周期。
- 文档先行的策略是对的——写文档的过程其实就是理清思路的过程。

## 第二周期（4.26 - 4.28）

### 一、核心产出

本周期交付的最满意成果：**完成 CLI 方向从功能实现到量化评测的完整闭环**。

实现了 `mem memorize`、`mem search`、`mem watch`、`mem workflow save/run`、`mem suggest` 等核心命令，打通了 SQLite 真实持久化链路，实现了渐进式降级（向量库异常时自动回退关键词搜索）、矛盾更新机制（新记忆自动覆盖旧记忆）、多维度智能排序（语义 + 频率 + 前缀 + 成功率 + 目录上下文）。最终建立了完整的测试与评测体系，全量测试 67 passed，评测指标全部达标。

### 三、过程复盘与沉淀

**1. 这周主要搞定了哪些具体环节？**

- **后端 API 开发**：让 AI 生成了 CLI 和 Memory 路由的初始代码，自己补充了矛盾更新逻辑和多维度排序算法。
- **真实数据库改造**：将临时数组存储替换为 SQLite 持久化。AI 帮忙生成了 SQLAlchemy 模型和迁移脚本，自己处理了向量库降级的边界逻辑。
- **测试体系搭建**：让 AI 生成单元测试框架，自己设计了 evaluation 测试数据集（6 条关键记忆 + 360 条干扰数据），AI 帮忙编写了自动验证脚本。
- **命令参数解析**：AI 生成了 `command_parser.py` 的初始版本，自己补充了 flags、positionals、paths 的边界处理。

**2. 过程中有没有遇到什么特别不顺、卡住很久的情况？**

- **向量库初始化失败**：ChromaDB 在某些环境下会因为路径权限问题初始化失败，导致整个保存流程崩溃。卡了将近 2 小时。
  - **破局方式**：加了 try-except 降级逻辑——向量库异常时仍然保存到关系库，标记 `vector_status=error`，后续可以手动恢复。这个"渐进式降级"的设计后来成了项目的核心亮点之一。
- **矛盾更新的 topic_key 匹配**：一开始用中文文本做 topic_key，结果"以后用 prod"和"改成用 prod"生成了不同的 key，导致矛盾检测失败。
  - **破局方式**：引入 project 字段作为 topic_key 的主要组成部分，中文文本只作为兜底。

**3. 有没有什么写得特别顺，下次还能复用的东西？**

- **渐进式降级模式**：`try: 主逻辑 except: 降级逻辑 + 标记状态`。这个模式在存储层、检索层、Embedding 层都用上了，非常实用。
- **Evaluation 测试数据集设计方法**：先定义关键记忆，再批量生成干扰数据，最后用自动化脚本验证 Hit@1/Hit@3/MRR。这个方法论可以复用到任何搜索/推荐场景。
- **AI 生成测试 + 人工补充边界**：让 AI 生成测试框架和常规用例，自己补充边界情况（空值、异常、并发），效率最高。

### 四、本周随手记

- 发现 AI 特别擅长生成"结构化代码"（路由、模型、CRUD），但对于"业务逻辑"（排序算法、降级策略）还是需要自己主导。
- 评测数据集的设计花了比预期多很多的时间，但这是值得的——有了量化数据，答辩时说话就有底气。
- `pytest -q -p no:cacheprovider` 这个命令组合很好用，安静输出且不缓存。

## 第三周期（4.29 - 5.1）

### 一、核心产出

本周期交付的最满意成果：**完成飞书方向核心功能闭环，并打通 CLI 与飞书的双向联动**。

新增飞书消息分析、项目决策抽取、决策结构化入库、历史记忆查询和主动推送能力。飞书群聊中的团队决策可以自动沉淀为长期记忆，并反向影响 CLI 命令推荐排序（例如废弃 staging 命令、上浮 prod 命令）。同时完成了飞书 SDK 长连接事件订阅方案，支持本地开发阶段直接监听飞书群消息。

| 指标 | 数据 |
|------|------|
| 代码提交 | 6 次 |
| 新增/修改文件 | ~20 个 |
| 测试用例 | 74 个（新增 7 个飞书相关） |

| AI 使用场景 | 决策抽取规则设计、SDK 接入代码生成、测试用例编写、文档撰写 |

### 三、过程复盘与沉淀

**1. 这周主要搞定了哪些具体环节？**

- **飞书决策路由开发**：让 AI 生成了 FastAPI 路由的初始代码和 Pydantic schema，自己编写了决策抽取的正则规则（DECISION_MARKERS、QUERY_MARKERS、project 提取、preferred/rejected terms 提取）。
- **SDK 接入**：AI 帮忙查阅 lark-oapi 文档并生成了消息发送和事件订阅的封装代码，自己处理了事件对象到内部消息结构的转换。
- **CLI 联动**：在 `cli.py` 的 suggest 接口中加入了读取 project_decision 记忆并重排结果的逻辑，这部分主要是自己写的。
- **文档同步**：让 AI 生成了飞书方向的 4 篇分阶段开发文档框架，自己补充了具体实现细节。

**2. 过程中有没有遇到什么特别不顺、卡住很久的情况？**

- **飞书 SDK 文档不全**：lark-oapi 的 Python SDK 文档示例较少，很多接口需要自己翻源码理解参数含义。花了大半天才把消息发送和事件订阅跑通。
  - **破局方式**：让 AI 帮忙读 SDK 源码并生成调用示例，然后自己在飞书开放平台上实际测试验证。
- **决策抽取的中文匹配**：正则表达式匹配中文关键词时，容易出现"以后统一用 prod"和"以后统一使用 prod"匹配不一致的问题。
  - **破局方式**：用 `统一用|统一使用|以后用|以后统一用` 多个模式覆盖不同表达方式。

**3. 有没有什么写得特别顺，下次还能复用的东西？**

- **飞书 SDK 封装模式**：`send_text_message()` 和 `send_card_message()` 的封装，带自动降级（卡片失败 → 文本）。这个模式在其他 SDK 接入场景也能复用。
- **决策抽取的"规则 + LLM 双保险"设计**：虽然这个周期只实现了规则抽取，但架构上预留了 LLM 接入点，下个周期直接填充即可。
- **事件对象转换函数**：`event_to_message_payload()` 把飞书 SDK 的事件对象转成统一的内部格式，解耦了 SDK 和业务逻辑。

### 四、本周随手记

- 飞书 SDK 的长连接方案比 HTTP 回调方案更适合本地开发——不需要公网地址，直接 `python scripts/run_feishu_sdk_events.py` 就能收到消息。
- 决策抽取的 topic_key 设计很关键：用 `decision:{chat_id}:{project}` 格式，既能区分不同群聊，又能区分不同项目，还能支持矛盾更新的精确匹配。
- 测试飞书功能时，mock 比真实调用方便太多——用 `FakeResponse` 和 `monkeypatch` 就能覆盖所有场景。

**2. 过程中有没有遇到什么特别不顺、卡住很久的情况？**

- **LLM 抽取的 Mock 测试**：在测试中 mock OpenAI API 时，monkeypatch 的目标路径总是搞不对。花了很长时间才发现需要 patch `core.decision_extractor._get_openai_client` 而不是 `openai.OpenAI`。
  - **破局方式**：直接在模块对象上 patch（`monkeypatch.setattr(de_mod, "_get_openai_client", lambda: fake_client)`），而不是用字符串路径。
- **飞书路由测试的 lark_oapi 依赖**：`handle_feishu_message` 会调用 `_send_group_card`，进而调用 lark-oapi SDK。在测试环境中 lark-oapi 未安装，导致测试失败。
  - **破局方式**：在测试中 monkeypatch `_send_group_card` 和 `_send_group_text`，绕过 SDK 依赖。
- **Windows 编码问题**：中文字符在 Windows 终端中偶尔出现乱码，影响测试输出的可读性。
  - **破局方式**：在关键位置加了 `sys.stdout.reconfigure(encoding='utf-8')`。

**3. 有没有什么写得特别顺，下次还能复用的东西？**

- **深层测试的"降级验证"方法**：先 mock 依赖使其抛异常，验证主逻辑是否正确降级。这个方法在存储层（向量库异常）、检索层（Embedding 异常）、抽取层（LLM 异常）都用上了。

- **环境变量开关设计**：`FEISHU_AUTO_REPLY=true` 和 `USE_LLM_DECISION_EXTRACTION=true` 的设计，让功能可以在不改代码的情况下开关。以后加新功能时会继续用这个模式。

  - **破局方式**：在 `_ensure_collection()` 中加入"写入测试向量"的检测逻辑，如果不匹配则调用 `delete_collection()` + `get_or_create_collection()` 彻底重建。
