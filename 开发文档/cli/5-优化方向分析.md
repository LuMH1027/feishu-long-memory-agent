# 方向 A：CLI 高频命令与工作流记忆优化方向分析

更新时间：2026-04-27

本文档基于题目要求和当前代码实现，分析 CLI 方向已经完成的能力、与赛题描述之间的差距，以及后续最值得投入的优化方向。

赛题方向 A 的核心要求：

> 开发者在终端中频繁输入长命令、复杂参数或项目路径。设计记忆系统，自动记录用户的高频命令模式、常用参数组合、项目路径偏好，并在用户输入前缀时自动补全或推荐。更进一步，能记住“在项目 A 中部署使用参数 X，在项目 B 中使用参数 Y”，实现上下文感知的命令建议。记忆特征：显式记忆（用户可主动教）+ 隐式记忆（系统统计频率自动总结）。

---

## 1. 当前代码能力盘点

### 1.1 已支持：显式记忆

对应代码：

- `cli/main.py`
  - `memorize()`
- `backend/routers/memory.py`
  - `extract_and_store_memory()`
  - `store_memory()`
- `core/storage.py`
  - `save_memory()`

当前用户可以通过：

```powershell
mem memorize "docker run -p 8080:80 -v /data:/app/data --name webapp my-image:1.2" --type "docker启动命令"
```

主动教给系统一条记忆。

调用链：

```text
mem memorize
  -> cli.main.memorize()
  -> POST /api/v1/memory/extract
  -> memory.extract_and_store_memory()
  -> memory.store_memory()
  -> core.storage.save_memory()
  -> SQLite memories 表
  -> Chroma 向量库
```

评价：已经满足“用户可主动教”的基础要求。

不足：当前 `mem memorize` 只能保存 content 和 type，不能显式传入项目路径、命令用途、标签、风险等级、适用环境等结构化上下文。

---

### 1.2 已支持：隐式高频命令统计

对应代码：

- `cli/main.py`
  - `watch()`
- `backend/routers/cli.py`
  - `record_command()`

当前用户可以通过：

```powershell
mem watch --shell powershell --auto-record-threshold 3
```

扫描 shell history，统计高频命令，并上报后端。

调用链：

```text
mem watch
  -> cli.main.watch()
  -> 读取 shell history
  -> Counter(commands)
  -> 过滤 count >= threshold 且长度 > 10 的命令
  -> POST /api/v1/cli/command/record
  -> cli.record_command()
  -> memories 表中写入或合并 type=cli_command 的记录
```

评价：已经满足“系统统计频率自动总结”的基础要求。

不足：

1. 目前只按完整命令字符串计数，不会抽象命令模式。
2. 只记录命令出现次数，不记录命令成功率。
3. 不分析命令参数结构，例如端口、镜像、命名空间、配置文件路径。
4. `watch()` 当前没有上报 directory，导致后端虽然支持 `directory` 字段，但实际扫描历史时没有项目路径上下文。

---

### 1.3 已支持：命令推荐和搜索

对应代码：

- `cli/main.py`
  - `search()`
  - `_search_memories()`
  - `_normalize_result()`
- `backend/routers/memory.py`
  - `search_memories()`
  - `retrieve_memories()`
  - `_search_db()`
  - `_memory_search_score()`
- `backend/routers/cli.py`
  - `suggest_command()`
- `core/retriever.py`
  - `search_memories()`
  - `calculate_cli_relevance_score()`

当前支持：

```powershell
mem search "启动webapp容器"
mem search "docker exited"
mem search "docker exited" --copy
mem search "docker exited" --execute
```

搜索调用顺序：

```text
_search_memories()
  1. GET /memory/search
  2. 如果失败或无结果，POST /memory/retrieve
  3. 如果仍无结果，POST /cli/command/suggest
```

评价：已经具备自然语言搜索、命令片段搜索、多级 fallback 和复制/执行能力。

不足：

1. 题目强调“用户输入前缀时自动补全或推荐”，当前实现是 `mem search` 主动搜索，还不是 shell 原生输入过程中的实时补全。
2. `/cli/command/suggest` 有 `directory` 参数，但当前没有参与过滤或排序。
3. 前缀匹配主要在 `core/retriever.py` 排序中使用，`suggest_command()` 仍然是 token 包含匹配，没有真正做“前缀输入推荐”的交互体验。

### 1.4 已支持：工作流记忆

对应代码：

- `cli/main.py`
  - `save_workflow()`
  - `run_workflow()`
- `backend/routers/memory.py`
  - `store_memory()`

当前用户可以保存多步工作流：

```powershell
mem workflow save "docker清理" "docker system prune -f" "docker volume prune -f"
```

然后执行：

```powershell
mem workflow run "docker清理"
```

调用链：

```text
mem workflow save
  -> cli.main.save_workflow()
  -> POST /api/v1/memory/
  -> memory.store_memory()
  -> core.storage.save_memory()
  -> memories 表，type=cli_workflow
```

```text
mem workflow run
  -> cli.main.run_workflow()
  -> _search_memories(name, 1, "cli_workflow")
  -> json.loads(content)
  -> 逐步 confirm
  -> subprocess.run(step, shell=True)
```

评价：工作流能力已经具备雏形，符合“复杂命令组合复用”的方向。

不足：

1. 工作流没有记录适用项目、适用环境、前置条件。
2. 工作流运行没有记录执行结果，无法反过来提升推荐排序。
3. 工作流步骤没有风险等级，例如删除、部署、生产环境操作需要更强确认。

## 2. 与赛题要求的差距

| 赛题要求 | 当前状态 | 差距 |
|---|---|---|
| 主动教记忆 | 已支持 `mem memorize` | 缺少结构化上下文 |
| 高频命令自动记录 | 已支持 `mem watch` | 只统计完整命令，不总结模式 |
| 常用参数组合记忆 | 部分支持，完整命令会被保存 | 未抽取参数组合 |
| 项目路径偏好 | 后端字段有 `directory`，但 CLI watch 未传 | 未形成可用能力 |
| 输入前缀自动补全 | 部分支持搜索和 suggest | 不是 shell 实时补全 |
| 项目 A 用参数 X，项目 B 用参数 Y | 尚不充分 | 缺少项目识别和上下文排序 |
| 显式 + 隐式结合 | 基础支持 | 缺少冲突合并、记忆更新、可信度 |
| 工作流记忆 | 已支持 save/run | 缺少上下文、结果反馈和风险控制 |

## 4. P0 优化一：项目上下文感知推荐

### 4.1 为什么重要

题目中特别强调：

> 在项目 A 中部署使用参数 X，在项目 B 中使用参数 Y。

这是方向 A 最有区分度的能力。如果只做 `mem search`，容易被认为是“命令历史搜索”。如果能根据当前目录自动推荐不同参数，就更像“开发者上下文记忆系统”。

### 4.2 当前代码基础

后端请求模型已经有字段：

```python
class CommandRecordRequest(BaseModel):
    command: str
    count: int
    shell: str
    directory: Optional[str] = None
    exit_code: Optional[int] = None
```

推荐请求也有：

```python
class CommandSuggestRequest(BaseModel):
    partial_command: str
    directory: Optional[str] = None
    shell: str = "powershell"
```

也就是说，数据结构已经预留了 `directory`，但当前利用不足。

### 4.3 建议实现

#### CLI 侧改造

在这些命令中传入当前目录：

- `mem watch`
- `mem search`
- 后续新增 `mem suggest`

示例：

```python
"directory": str(Path.cwd())
```

`mem search` 调用 `_search_memories()` 时，也可以把当前目录传给后端。

#### 后端记录逻辑

`record_command()` 中已保存：

```python
metadata["directory"] = request.directory
```

建议进一步增加：

```text
project_root
project_name
git_remote
language_stack
```

项目识别规则可以从简单到复杂：

1. 当前目录是否在 Git 仓库内。
2. Git 仓库根目录名作为 project_name。
3. `git remote get-url origin` 作为 project_id。
4. 根据 `package.json`、`pyproject.toml`、`pom.xml`、`go.mod` 判断项目类型。

#### 推荐排序逻辑

在 `/cli/command/suggest` 和 `/memory/search` 中加入目录相关性：

```text
同 project_id：+0.4
同 project_root：+0.3
同目录前缀：+0.2
同语言栈：+0.1
```

### 4.4 预期效果

同样查询：

```powershell
mem search "部署后端"
```

在项目 A 目录下返回：

```text
kubectl rollout restart deploy/api-server -n staging
```

在项目 B 目录下返回：

```text
kubectl rollout restart deploy/api-server -n prod
```

这正好对应赛题示例。

### 4.5 涉及文件

- `cli/main.py`
  - `_search_memories()`
  - `search()`
  - `watch()`
- `backend/routers/cli.py`
  - `CommandRecordRequest`
  - `CommandSuggestRequest`
  - `record_command()`
  - `suggest_command()`
- `backend/routers/memory.py`
  - `_sort_and_limit()`
- `core/retriever.py`
  - `calculate_cli_relevance_score()`

## 5. P0 优化二：命令参数模式抽取

### 5.1 为什么重要

当前系统保存的是完整命令。例如：

```text
docker run -p 8080:80 -v /data:/app/data --name webapp my-image:1.2
```

但题目强调“高频命令模式、常用参数组合”。这意味着系统不应只记字符串，还应该理解：

```text
命令主体：docker run
端口参数：-p 8080:80
挂载参数：-v /data:/app/data
容器名：--name webapp
镜像：my-image:1.2
```

### 5.2 建议实现

新增命令解析模块：

```text
core/command_parser.py
```

输入：

```text
docker run -p 8080:80 -v /data:/app/data --name webapp my-image:1.2
```

输出：

```json
{
  "program": "docker",
  "subcommand": "run",
  "command_family": "docker run",
  "flags": {
    "-p": "8080:80",
    "-v": "/data:/app/data",
    "--name": "webapp"
  },
  "positionals": ["my-image:1.2"],
  "paths": ["/data", "/app/data"],
  "risk_level": "medium"
}
```

保存到 `memory_metadata`：

```json
{
  "count": 5,
  "shell": "powershell",
  "directory": "E:/project-a",
  "command_family": "docker run",
  "flags": {
    "-p": "8080:80",
    "-v": "/data:/app/data",
    "--name": "webapp"
  }
}
```

### 5.3 推荐排序增强

当用户输入：

```text
docker run webapp
```

系统不只匹配全文，还可以匹配：

- `program=docker`
- `subcommand=run`
- `--name=webapp`
- 镜像名

### 5.4 涉及文件

- 新增 `core/command_parser.py`
- 修改 `backend/routers/cli.py: record_command()`
- 修改 `backend/routers/cli.py: suggest_command()`
- 修改 `tests/unit/test_backend_cli_api.py`
- 修改 `tests/unit/test_core_components.py`

## 6. P1 优化三：Shell 前缀补全集成

### 6.1 为什么重要

题目说的是：

> 在用户输入前缀时自动补全或推荐。

当前体验是：

```powershell
mem search "docker"
```

这属于主动搜索，还不是终端输入中的补全。

### 6.2 建议实现

新增命令：

```powershell
mem suggest "docker ru"
```

或者：

```powershell
mem complete "docker ru" --shell powershell
```

返回纯文本候选，方便 shell completion 脚本消费：

```text
docker run -p 8080:80 -v /data:/app/data --name webapp my-image:1.2
docker run --rm hello-world
```

PowerShell 可以接入 argument completer：

```powershell
Register-ArgumentCompleter -Native -CommandName memrun -ScriptBlock {
    param($wordToComplete, $commandAst, $cursorPosition)
    mem suggest $wordToComplete
}
```

### 6.3 技术路线

```text
shell 输入前缀
  -> completion hook
  -> mem suggest <prefix>
  -> POST /api/v1/cli/command/suggest
  -> 返回候选命令
  -> shell 展示补全项
```

### 6.4 涉及文件

- `cli/main.py`
  - 新增 `suggest()` 或 `complete()`
- `backend/routers/cli.py`
  - 强化 `suggest_command()`
- 新增 `scripts/completion/powershell.ps1`
- 新增 `scripts/completion/bash.sh`

## 7. P1 优化四：矛盾更新和记忆覆盖

### 7.1 为什么重要

长期记忆系统不能只追加，不处理冲突。否则用户说：

```text
以后周报发给 A
不对，以后周报发给 B
```

系统如果还推荐 A，会显得不可信。

### 7.2 当前状态

当前参赛测试数据集中已经设计了矛盾更新测试：

```text
test/data/cli_effectiveness_dataset.json
```

但代码层面还没有完整的“识别旧记忆并覆盖”的机制。

### 7.3 建议实现

新增记忆状态字段或 metadata：

```json
{
  "status": "active",
  "supersedes": "old-memory-id",
  "superseded_by": "new-memory-id",
  "topic_key": "weekly_report_recipient"
}
```

保存新记忆时：

1. 检测文本中是否有更新意图：
   - 不对
   - 更正
   - 改成
   - 以后用
   - 不再使用
2. 生成或抽取 `topic_key`。
3. 搜索同 topic 的旧记忆。
4. 将旧记忆标记为 `inactive` 或降低排序权重。
5. 新记忆设为 `active`。

### 7.4 涉及文件

- `backend/routers/memory.py`
  - `store_memory()`
  - `extract_and_store_memory()`
- `core/storage.py`
  - `save_memory()`
- `core/retriever.py`
  - 排序时过滤或降权 inactive 记忆
- `db/relational/models.py`
  - 可考虑新增字段，或暂存于 `memory_metadata`

## 8. P1 优化五：命令执行反馈闭环

### 8.1 为什么重要

当前系统记录了命令出现频率，但没有记录：

- 命令是否执行成功
- 平均耗时
- 最近失败原因
- 是否被用户复制后真正执行

这些信息可以直接影响推荐质量。

### 8.2 建议实现

对 `mem search --execute` 和 `workflow run` 增加执行结果记录。

当前代码：

```python
subprocess.run(cmd, shell=True)
```

建议改成：

```python
result = subprocess.run(cmd, shell=True)
```

然后上报：

```text
POST /api/v1/cli/command/record
```

带上：

```json
{
  "command": "...",
  "count": 1,
  "shell": "powershell",
  "directory": "...",
  "exit_code": 0
}
```

后端 metadata 增加：

```json
{
  "success_count": 10,
  "failure_count": 1,
  "last_exit_code": 0,
  "last_failed_at": null
}
```

排序时：

```text
成功率高：加权
最近失败：降权
危险命令：需要确认
```

### 8.3 涉及文件

- `cli/main.py`
  - `search()`
  - `run_workflow()`
- `backend/routers/cli.py`
  - `record_command()`
- `core/retriever.py`
  - `calculate_cli_relevance_score()`

## 9. P2 优化六：工作流上下文和风险控制

### 9.1 当前问题

工作流目前只有：

```json
{
  "name": "...",
  "steps": [...],
  "created_at": "..."
}
```

缺少：

- 项目
- 环境
- 风险等级
- 是否需要逐步确认

  "name": "部署webapp",

## 11. P2 优化八：编码和中文显示清理

### 11.1 当前问题

当前部分源码、测试断言和终端输出中出现中文乱码，例如：

```text
鉁?璁板繂宸蹭繚瀛?
```

这不影响核心逻辑，但会影响演示观感和文档可读性。

### 11.2 建议处理

统一：

- 源码文件编码：UTF-8
- 终端输出：明确中文字符串
- 测试断言：改成稳定英文 key 或中文 UTF-8
- PowerShell 环境：建议设置 `chcp 65001`

### 11.3 涉及文件
