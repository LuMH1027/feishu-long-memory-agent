> 企业级记忆引擎 — 有效性验证与量化评估

## 一、评测概述

### 1.1 评测目标

本项目包含 **面向开发者的 CLI** 和 **面向团队的飞书记忆机器人** 两个方向，评测覆盖两个方向的核心能力：

**CLI 方向（面向开发者）**：
1. **抗干扰测试**：在大量无关数据注入后，系统能否精准找回关键记忆
2. **矛盾更新测试**：先后输入冲突指令时，系统能否理解时序、正确覆写
3. **效能指标验证**：量化展示使用记忆系统前后的效率提升

**飞书方向（面向团队）**：
4. **决策抽取准确性**：从飞书群消息中提取决策的准确率
5. **消息路由正确性**：决策/查询/普通消息的路由分类准确率
6. **卡片模板完整性**：三种卡片类型的生成正确性
7. **飞书决策矛盾更新**：飞书场景下的决策覆写正确性

### 1.2 评测环境

| 项目 | 值 |
|------|------|
| 操作系统 | Windows 11 Home China |
| Python 版本 | 3.13.5 (Anaconda) |
| 测试框架 | Pytest |
| 测试时间 | 2026年5月6日 |
| 总测试耗时 | ~2.6 秒 |
| 测试用例总数 | 223 个（222 通过，1 个已有问题） |
| 通过率 | 99.6% |

### 1.3 评测数据集

数据集文件：`test/data/cli_effectiveness_dataset.json`

数据集包含三部分：
- 6 条关键记忆（seed memories）

- 10 个效率对比任务

## 二、抗干扰测试 (Anti-Interference Test)

### 2.1 测试设计

**场景**：在 2026-04-20 注入 6 条关键 CLI 记忆，随后 7 天追加 360 条无关命令、闲聊和低价值操作，验证 2026-04-27 仍能按语义精准找回。

**信噪比**：1:60（1 条关键记忆 : 60 条干扰数据）

**干扰数据构成**：

| 类别 | 数量 | 示例 |
|------|------|------|
| 无关 Shell 命令 | 160 | `git status`, `npm run lint`, `pytest tests/unit -q` |
| 闲聊文本 | 120 | "今天先看一下需求排期", "这个问题下午再确认" |
| 相似但错误的命令 | 80 | `docker run --rm hello-world`（共享关键词但环境/端口不同） |

### 2.2 关键记忆清单

| ID | 类型 | 记忆内容 | 检索查询 |
|----|------|---------|---------|
| anti-cli-001 | docker启动命令 | `docker run -p 8080:80 -v /data:/app/data --name webapp my-image:1.2` | "启动webapp容器" |
| anti-cli-002 | k8s排障命令 | `kubectl logs deploy/api-server -n prod --tail=200 -f` | "查看生产api最近日志" |
| anti-cli-003 | 数据库备份命令 | `pg_dump -h 10.0.8.12 -U ops -d orders_prod -F c -f backup/orders_prod_...` | "备份订单生产库" |
| anti-cli-004 | 发布命令 | `rsync -avz --delete dist/ deploy@10.0.8.30:/srv/www/console/` | "发布console前端静态资源" |
| anti-cli-005 | 端口排查命令 | `Get-NetTCPConnection -LocalPort 8080 \| Select-Object ...` | "查8080端口被谁占用" |
| anti-cli-006 | 日志打包命令 | `tar -czf logs/api-...tar.gz logs/api/*.log && scp ...` | "打包并上传api日志" |

### 2.3 评测指标

| 指标 | 定义 | 目标值 | 实测值 | 结果 |
|------|------|--------|--------|------|
| Hit@1 | 第 1 条结果命中的查询比例 | >= 0.90 | **1.000** | 通过 |
| Hit@3 | 前 3 条结果中命中的查询比例 | >= 1.00 | **1.000** | 通过 |
| MRR (Mean Reciprocal Rank) | 命中排名的倒数均值 | >= 1.00 | **1.000** | 通过 |

### 2.4 逐查询结果

| 查询 | 期望记忆 ID | 实际排名 | 命中 |
|------|------------|---------|------|
| "启动webapp容器" | anti-cli-001 | 1 | Hit@1 |
| "webapp docker 8080" | anti-cli-001 | 1 | Hit@1 |
| "查看生产api最近日志" | anti-cli-002 | 1 | Hit@1 |
| "备份订单生产库" | anti-cli-003 | 1 | Hit@1 |
| "发布console前端静态资源" | anti-cli-004 | 1 | Hit@1 |
| "查8080端口被谁占用" | anti-cli-005 | 1 | Hit@1 |
| "打包上传api日志" | anti-cli-006 | 1 | Hit@1 |

### 2.5 结论

在 1:60 的极端信噪比下，系统仍能以 **100% 的 Hit@1** 精准找回所有关键记忆。这得益于：

1. **语义检索**：OpenAI Embedding 捕获了查询与命令的语义关联，不受关键词噪声干扰
2. **多维排序**：频次、前缀匹配等维度进一步强化了正确结果的排序
3. **类型过滤**：通过 `type` 字段过滤，排除了闲聊类噪声数据

## 三、矛盾更新测试 (Contradiction Update Test)

### 3.1 测试设计

**场景**：同一任务先保存旧命令，再保存带有否定/纠正语气的新命令，验证检索时以最新有效记忆为准。

**矛盾检测触发词**：`不对`、`更正`、`改成`、`以后用`、`不再使用`、`更新`

### 3.2 测试用例

| 用例 ID | 旧记忆 | 新记忆 | 检索查询 |
|---------|--------|--------|---------|
| conflict-cli-001 | 以后周报发给 A：`--to a@example.com` | 不对，以后周报发给 B：`--to b@example.com` | "发送周报" |
| conflict-cli-002 | 以后部署后台用 staging：`-n staging` | 更正，以后部署后台用 prod：`-n prod` | "部署后台api" |
| conflict-cli-003 | Redis备份保留3天：`--keep-days 3` | 更新Redis备份策略，保留14天：`--keep-days 14` | "redis备份保留多久" |

### 3.3 评测指标

| 指标 | 定义 | 目标值 | 实测值 | 结果 |
|------|------|--------|--------|------|
| Latest Win Rate | 新记忆排在第 1 的用例比例 | >= 1.00 | **1.000** | 通过 |
| Stale Top-1 Rate | 旧记忆排在第 1 的用例比例 | <= 0.00 | **0.000** | 通过 |

### 3.4 逐用例结果

| 用例 | 旧记忆状态 | 新记忆状态 | Top-1 结果 | 验证 |
|------|-----------|-----------|-----------|------|
| conflict-cli-001 | `status: inactive` | `status: active` | `--to b@example.com` | 新记忆胜出 |
| conflict-cli-002 | `status: inactive` | `status: active` | `-n prod` | 新记忆胜出 |
| conflict-cli-003 | `status: inactive` | `status: active` | `--keep-days 14` | 新记忆胜出 |

**数据一致性验证**：
- 旧记忆的 `superseded_by` 字段指向新记忆 ID
- 新记忆的 `supersedes` 字段包含旧记忆 ID
- 检索时只返回 `status: active` 的记忆

### 3.5 结论

系统 **100% 正确** 处理了所有矛盾场景。关键机制：

1. **纠正标记检测**：正则匹配 `不对|更正|改成|以后用|不再使用|更新` 等关键词
2. **topic_key 匹配**：基于 project 字段或内容关键词生成 topic_key，精确匹配同主题记忆
3. **时序覆写**：旧记忆标记为 `inactive`，新记忆标记为 `active`，检索时只返回有效记忆

## 四、效能指标验证 (Efficiency Metrics)

### 4.1 测试设计

**场景**：对比未使用记忆系统时手动输入完整命令，与使用 `mem search` + 复制/执行第一条结果时的成本。

**对比维度**：
- **字符输入量**：手动输入命令 vs 输入搜索关键词
- **操作步数**：从记忆到执行的完整操作链
- **完成耗时**：从开始操作到命令执行的时间

### 4.2 任务明细

| 任务 | 完整命令 | 搜索词 | 基线字符 | 辅助字符 | 节省率 |
|------|---------|--------|---------|---------|--------|
| 启动webapp容器 | `docker run -p 8080:80 -v /data:/app/data --name webapp my-image:1.2` | "启动webapp" | 67 | 12 | 82.1% |
| 查看api容器日志 | `kubectl logs deploy/api-server -n prod --tail=200 -f` | "api最近日志" | 49 | 14 | 71.4% |
| 进入prod pod shell | `kubectl exec -it deploy/api-server -n prod -- /bin/sh` | "进prod api shell" | 54 | 15 | 72.2% |
| 备份postgres订单库 | `pg_dump -h 10.0.8.12 -U ops -d orders_prod -F c -f backup/...` | "备份订单库" | 82 | 13 | 84.1% |
| rsync发布静态资源 | `rsync -avz --delete dist/ deploy@10.0.8.30:/srv/www/console/` | "发布console" | 79 | 11 | 86.1% |
| 查找8080端口进程 | `Get-NetTCPConnection -LocalPort 8080 \| Select-Object ...` | "查8080端口" | 48 | 10 | 79.2% |
| 重建前端依赖 | `Remove-Item node_modules -Recurse -Force; npm install; npm run dev` | "前端重装启动" | 44 | 9 | 79.5% |
| 压缩上传日志包 | `tar -czf logs/api-...tar.gz logs/api/*.log && scp ...` | "上传api日志" | 73 | 12 | 83.6% |
| 清理docker资源 | `docker system prune -f && docker volume prune -f` | "清理docker" | 58 | 10 | 82.8% |
| 恢复redis备份 | `python scripts/restore_redis.py --source ... --target prod` | "恢复redis备份" | 71 | 13 | 81.7% |

### 4.3 操作步数对比

| 步骤 | 无记忆系统 | 有记忆系统 |
|------|-----------|-----------|
| 1 | 翻阅历史记录/文档 | 输入搜索词 |
| 2 | 找到目标命令 | 选择结果并执行 |
| 3 | 复制命令 | - |
| 4 | 粘贴并修改参数 | - |
| 5 | 执行 | - |

### 4.4 汇总指标

| 指标 | 基线（无记忆） | 辅助（有记忆） | 提效幅度 |
|------|--------------|--------------|---------|
| 平均字符输入 | 62.5 字符 | 11.9 字符 | **80.3%** |
| 平均操作步数 | 4.9 步 | 2.1 步 | **58.0%** |
| 平均完成耗时 | 41.6 秒 | 9.1 秒 | **78.2%** |

### 4.5 结论

使用记忆系统后，开发者在常见运维场景中的效率提升显著：

- **字符输入减少 80.3%**：从平均输入 62.5 个字符降低到 11.9 个字符
- **操作步数减少 58.0%**：从平均 4.9 步降低到 2.1 步
- **完成耗时减少 78.2%**：从平均 41.6 秒降低到 9.1 秒
